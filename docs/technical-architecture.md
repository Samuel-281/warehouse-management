## 2. 当前阶段目标

当前系统已经用 Next.js、Prisma 和 PostgreSQL 跑通核心业务流程。下一阶段目标是完成 1.0 发布收口，并部署到阿里云 ECS。

本阶段优先完成：

1. 保持电脑端核心业务稳定。
2. 保持页面权限和 API 权限一致。
3. 通过 Prisma migration 管理生产数据库结构。
4. 在 ECS 上用 Nginx + PM2 + PostgreSQL 同机部署。
5. PDA 入口暂保留草图，待设备到货后再做正式闭环。

## 5. 数据流设计

正式落地后的数据流：

1. 用户在电脑端页面操作；PDA 暂为草图入口。
2. 页面调用 Next.js API Route。
3. API Route 调用业务服务层。
4. 服务层校验业务规则。
5. 数据访问层通过 Prisma 写入 PostgreSQL。
6. 所有会改变库存归属的操作同时写入不可变库存流水。
7. 页面重新查询库存或局部刷新。

## 6. 核心业务服务

建议逐步建立以下服务：

| 服务 | 职责 |
| --- | --- |
| `master-data-service` | 维护货物、仓库、库位、销售人员、终端店铺 |
| `inbound-service` | 厂家到货入库、终端店铺退换货入库 |
| `outbound-service` | 挪仓、销售出库 |
| `sales-return-service` | 销售人员未售完货物回流仓库 |
| `inventory-service` | 库存查询、条码详情、库存流水查询 |
| `auth-service` | 登录、用户、角色和权限 |

## 7. 关键业务规则落点

业务规则不应只写在前端页面里。正式落地时需要在服务层再次校验：

1. 单件条码不可重复。
2. 终端店铺退换货入库必须登记生产日期。
3. 保健酒保质期默认为生产日期三年后。
4. 白酒默认无保质期。
5. 挪仓支持总仓和分仓之间互相流转。
6. 销售出库可从总仓或分仓发出。
7. 销售出库只分配到销售人员，不分配到终端店铺。
8. 销售退回只把销售人员名下条码回流到仓库，不重新计算生产日期和保质期。
9. 每次库存归属变化都必须写库存流水。

## 8. 接口规划

当前接口已覆盖基础资料和核心库存业务：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/master-data` | 获取货物、仓库、库位、销售人员、终端店铺 |
| `POST` | `/api/goods` | 新增货物 |
| `POST` | `/api/warehouses` | 新增分仓并生成默认库位 |
| `POST` | `/api/salespeople` | 新增销售人员 |
| `POST` | `/api/terminal-stores` | 新增终端店铺 |

第二批接口覆盖库存业务：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/inbound` | 提交入库 |
| `POST` | `/api/outbound` | 提交挪仓或销售出库 |
| `POST` | `/api/sales-returns` | 提交销售退回 |
| `GET` | `/api/inventory` | 查询库存 |
| `GET` | `/api/inventory/[barcode]` | 查询单件条码详情和流转 |

## 9. 迁移策略

为了降低风险，不一次性重写原型。

建议顺序：

1. 新增 Prisma 和数据库模型。
2. 初始化种子数据，使页面初始数据与当前原型一致。
3. 将基础资料页面接入 API。
4. 将入库接入 API。
5. 将出库接入 API。
6. 将销售退回接入 API。
7. 将库存查询和条码详情接入 API。
8. 再开始 UI 和交互重构。

## 10. 部署建议

第一版可按局域网部署设计：

1. 一台内网服务器运行 PostgreSQL。
2. 同一台或另一台服务器运行 Next.js 应用。
3. 电脑浏览器访问内网地址。
4. PDA 通过同一内网地址访问 PDA 页面。
5. 数据库定时备份。

正式部署前应补充：

1. 登录权限。
2. 操作日志。
3. 数据备份策略。
4. 异常处理和错误日志。
5. 基础安全配置。
